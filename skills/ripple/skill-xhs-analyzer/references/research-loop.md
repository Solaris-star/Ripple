# 多篇远端研究循环：有界、可恢复、尊重平台限制

本文件只在需要读取多篇小红书远端详情时使用。单篇分析、已有结果整理、纯离线统计不需要启动循环。

## 目标

- 控制请求范围，避免一次任务无限扩大。
- 串行处理容易触发平台限制的详情读取，并在每项后保存进度。
- 遇到验证码、NeedVerify、登录过期、明确封禁等信号时停止受影响的远端分支，不尝试规避平台防护。
- 即使远端分支受阻，也保留已经合法取得的数据，允许完成可做的离线分析并明确覆盖缺口。

## 不做的事

- 不通过随机 jitter、模拟“像人在读”、混入点赞/滚动等行为来规避反自动化检测。
- 不提供 Fast 模式去突破平台限制，也不因用户确认就自动穿过验证码/封禁。
- 不并发扇出大量 cookie-bound 详情请求。
- 不承诺某个固定“安全请求速率”；平台规则和限制会变化。

## 任务触发

先根据用户问题确定需要的样本规模。能用搜索/列表结果回答的，不额外打开每篇详情；需要正文、评论或单篇结构证据时才进入详情读取。

小任务可以直接维护一个内存/简单列表；只有样本较多、任务跨会话或需要断点恢复时，才建立 job 目录与队列文件。不要为了流程完整给三五篇研究创建复杂后台系统。

## 有界队列

长任务可使用：

```text
research/xhs/<job-slug>/
├── queue.jsonl        # 待处理项及状态
├── results/           # 已完成结果
├── loop-state.json    # 预算、最近状态、breaker
└── SUMMARY.md         # 最终/部分完成总结
```

建议状态：

```json
{
  "requested": 20,
  "completed": 7,
  "errors": 1,
  "breaker": "ok",
  "breakerReason": ""
}
```

预算来自用户目标、任务时限和平台当前允许的访问方式，不使用“默认每天 200 篇”之类无法保证长期成立的硬数字。

## 每一项怎么处理

1. 读取下一项和当前任务预算。
2. 如果当前运行时没有对应 CLI/受控工具，停止远端执行，保留队列并报告能力缺口。
3. 执行一次必要的读取，不并发扇出详情页。
4. 对结果分类：
   - **成功**：保存结果，标记 done。
   - **普通 404/内容不存在**：标记 unavailable/error，继续下一项。
   - **空 `{}` / token 可能失效**：可通过正常 search/list 入口重新获取该条上下文一次；仍为空则标记 unavailable，不把整个任务自动熔断。
   - **登录过期**：暂停需要登录的远端分支，提示用户通过允许的登录流程处理；离线结果仍可继续分析。
   - **NeedVerify / 验证码 / 明确 anti-bot 提示 / IP blocked 300012**：触发 breaker，停止后续远端读取，不自动重试穿过验证，也不自动换指纹/网络规避。
5. 写入进度后再处理下一项。

## 请求节奏

- 对 cookie-bound 详情端点默认串行；并发度 1 是本 CLI 的保守执行策略，不宣称是平台“安全阈值”。
- 间隔优先使用服务/CLI 已声明的限流信息或当前后端返回的 retry-after；没有明确信息时采用保守节奏，避免紧循环。
- 不为了赶截止时间切换到高频模式。需要更快时，优先缩小样本、改用公开列表/缓存/已有数据，或让用户确认减少覆盖范围。

## 重试

- 网络瞬断、普通 5xx 可以做有限重试；每次重试都要有上限和退避。
- 验证码、NeedVerify、登录失效、明确封禁不属于普通重试错误。
- 同一条连续失败且错误类型没有变化时停止重复尝试，记录原因后继续可完成部分或结束为 partial。

## 后台/跨会话

只有当前 Runtime 实际提供后台调度能力时才承诺后台继续。没有调度工具时，把队列和进度落盘后告诉用户当前已完成范围，不虚构 `/loop`、ScheduleWakeup 或 recurring issue 一定可用。

## 完成标准

- **完成**：达到用户要求的样本/证据覆盖，并生成总结。
- **部分完成**：已有数据足以给出部分结论，但部分远端数据因权限、平台限制或缺失未取得；报告覆盖率和缺口。
- **阻塞**：核心问题依赖的远端数据完全无法取得，且现有数据不足以回答。
- 无论哪种状态，都保留已完成结果，不因一个受阻条目丢弃整个研究。
