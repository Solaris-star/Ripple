# Plan: 小红书官方活动范围、默认/最新排序与分页

状态：PLAN，待用户确认后执行。基线：db5e570（main）。

## Goal / Non-goals

目标：在 Ripple 的小红书官方活动视图中，沿用所选账号创作者活动中心的活动 ID 集合及两种官方返回顺序；整个活动页实行有界分页，每页 10 条。明确区分已同步的官方列表、详情完整程度、当前筛选结果和历史记录。

非目标：不扩展 Ditto 规则/图片解析，不修改其他平台采集与排序规则，不重新登录或导出 Cookie，不执行报名、关注、收藏到小红书、投稿等外部写入，不删除历史 Campaign/本地收藏/选题引用。

## Success criteria（可验证）

1. 同一账号、同次验证、相同官方筛选参数下，分别比对默认与最新排序的完整 activity_id 序列；Ripple 的官方页序列与其对应来源快照一致，不以数量相等替代集合和顺序比对。核对官网前 3 页与尾页的标题、ID、基础信息；截图中列出的科技、AI、howto 活动用于遗漏回归检查。
2. 小红书视图显示“默认排序 / 最新排序”。不使用 updated_at、资格、收藏、规则完整度、活动 ID 大小或本地画像替代官方顺序。不同 activity_id 即使标题或详情链接相同也不合并；手工导入兼容仅在没有官方 ID 冲突时适用。
3. 一页最多渲染 10 张活动卡，桌面两列五行，窄屏一列且仍为每页 10 条。提供上一页、页码、省略号、下一页、首尾边界禁用，以及“共 N 条 · 第 X–Y 条 · P/Q 页”。页数由实际筛选总数计算，不硬编码 25 页或 250 条。
4. 筛选在分页前执行；切换平台、账号、排序或过滤条件回到第 1 页；详情/收藏操作不无故重置页码。后台更新不在用户翻页中途混入不同批次的官方顺序；缩页时安全校正页码。请求乱序不覆盖较新的页面状态。
5. 页码切换只读本地已同步数据，不反复启动浏览器或重复采集 250 个详情。失败保留原快照并显示过期/失败状态，缺少某排序快照时不冒用另一排序或本地推断。
6. API 页面响应最多 10 条，包含准确 total/page/page_size/total_pages/排序/快照时间与状态；总览统计和筛选选项不能因只加载一页而只统计这 10 条。
7. 旧无分页读取调用保持兼容；自动同步、详情补全、本地收藏和关联选题继续工作。运行定向测试、全量测试、前端构建及真实页面交互验收，完成后提交代码，不自动推送或重启服务。

## Context & assumptions（含补全部分）

### 本轮只读证据

- 当前 HEAD=db5e570，检查时工作区干净。
- 运行快照与 Campaign 库均有 250 条小红书活动。本轮针对截图核对的 15 个科技/AI/howto 活动均存在；这不能单独证明平台全量无遗漏。
- 部分活动在采集快照中的序号：小红书火箭队 42，超有趣小工具必吃榜 55，硬核测评局招募 59，2026云栖大会 87，科技数码生活手账 127，我这行的AI路 135，AI进化生活 234，howto创意剪辑 239。
- CampaignsPage.tsx:532–564 使用本地推荐分数排序，new 使用 updated_at。该文件约 908 行直接 visible.map，无分页。
- web/app.py:4669 的 GET /api/campaigns 返回全量数组。写入顺序与官方列表顺序没有独立保存。
- 在当前绑定账号的隔离浏览器中访问 creator.xiaohongshu.com/new/events，点击“默认排序 → 最新排序 → 默认排序”，确认请求为 GET /api/galaxy/v2/creator/activity_center/list：默认 sort=1，最新 sort=2；其余已观察参数 type=1、source=3、topic_activity=0。两种排序本次各返回 250 条，页面首屏顺序与各自响应相符。
- 当前账号官网默认首屏是 Pick你的每周时刻、音乐节、原神等；与用户截图的科技/AI前置不同。差异是否来自账号上下文、平台分组或其他条件尚未证实，不能宣称已复刻截图顺序，也不能自行构造推荐权重。

### 本计划的默认产品取舍（可在确认时调整）

- 每页固定 10 条，无“展示全部”或无限追加。
- 分页覆盖整个活动页；小红书筛选视图用官方默认/最新排序，其余平台和跨平台视图维持原有排序语义。
- 小红书官方视图只按该账号该排序快照中的成员分页；历史清单外活动及手工导入保留在全部平台/本地收藏等现有非官方视图，不删除数据、不混入官网页序。
- “已收藏”继续指 Ripple 本地收藏，不同步修改小红书收藏。
- 官方排序的对照账号为当前选择的已连接账号。截图若来自其他账号，需要使用该账号的授权登录态另行对照，不能用当前测试账号的结果承诺跨账号一致。

## Options considered → 推荐

A. 前端将全量数组 slice 分页：改动少，但仍传输整个库，筛选/排序继续容易与来源失去一致性。
B. 官方有序快照 + 后端分页查询 + 前端只渲染当前页：多一个兼容分页接口，能统一成员范围、计数与官方页序。推荐 B。

不选择每翻页都访问小红书：会增加浏览器启动、接口请求和账号占用，当前官方列表响应已经包含完整观察到的清单。

## Phases / Steps

### Step 1：确认两种来源序列并按账号保存

文件：ripple/xhs_browser.py、ripple/xhs_ops.py、ripple/campaign_sources.py；验证 tests/test_xhs_ops.py、tests/test_campaign_sources.py。

- 同一隔离浏览器会话中用官网实际排序交互或已验证的等价读取，分别捕获 sort=1 与 sort=2 的列表响应；严格匹配 host/path/请求参数/业务成功状态，避免晚到或其他类型列表串入。
- 返回有界、脱敏的活动实体、两套有序 ID 序列及请求条件、抓取时间、原始数、唯一数、截断状态；不把任何响应头、Cookie、凭据写入 Campaign。
- 顺序缓存按账号和排序分别保存，可扩展现有 campaign-sources.json 的 xiaohongshu 状态，不引入数据库。保存有界前后快照供翻页稳定使用；各排序失败独立保留旧数据并标记 stale。
- 列表读取与详情补全预算分离；两种排序共用详情缓存，不翻倍解析详情。修正 detail_limit=0 被 or 12 覆盖的问题，保证列表核验可禁用详情请求。
- 保留安全上限，达到上限时显式标记 truncated/incomplete，不宣称“全部”。

### Step 2：让 Campaign 查询沿用官方顺序

文件：web/app.py、ripple/campaign_sources.py；验证 tests/test_campaigns.py。

- 合并优先按 provider + activity_id 精确匹配，有冲突官方 ID 时禁止 URL/标题回退误合并。
- 官方顺序和当前成员范围从所选账号来源快照读取，不从 Campaign updated_at 推算。资格和收藏的变化不改变官方排名；保存规则字段和排名字段的职责分离。
- 添加 GET /api/campaigns/page，必须注册在 /api/campaigns/{cid} 前，避免路由遮蔽。保留旧 GET /api/campaigns 的数组形态。
- 查询参数包含 platform、account_id、sort、page、page_size=10、既有筛选项及 snapshot_id。小红书官方顺序使用 default/latest；跨平台保留现有排序模式。响应提供 items、total、page、page_size、total_pages、source_total、sort、snapshot_id、fetched_at、source_status、truncated，以及全结果统计/筛选选项。
- 先根据所选来源成员与筛选条件确定结果，再按官方位置排序，最后分页。无效/越界参数安全处理；未知排序不得静默替换。
- 无快照、超期、账号不可用、单排序失败提供可解释状态；不把缺少新快照当作 0 个活动。

### Step 3：前端分页与官方排序交互

文件：web/frontend/src/lib/api.ts、web/frontend/src/components/CampaignsPage.tsx、web/frontend/src/styles/index.css。

- 增加分页响应类型与 fetchCampaignPage，活动列表不再全量 visible.map。详情仍由现有详情接口读取。
- 小红书视图替换“推荐排序 / 最近更新”为“默认排序 / 最新排序”；不对后端官方结果二次打分。
- 固定每页10张，保留现有卡片字段与两列布局，加入页码控件与总数/范围。其他平台也按10条分页，保留其既有排序规则。
- 同步 load、refreshNow、收藏、编辑、详情关闭后的重载路径；取消/忽略旧请求，切换条件回首页，详情操作保留当前页。新快照到来提示更新；换到新批次时防止页码越界。
- 总览统计/下拉选项使用后端全结果统计，禁止使用当前10张卡片推算总量。

### Step 4：从用户视角验收

- 官方同一账号两种排序分别核对前3页和尾页；比较完整有序ID列表、集合差异和缺失项，报告具体缺失原因，不用测试通过数代替页面验收。
- 分页场景：0/1/10/11/250条、尾页不足10条、同标题不同ID、相同URL不同ID、过滤后总页数缩小、页码边界、排序切换、账号切换、慢请求覆盖、后台刷新、登录失效、保留历史收藏。
- 运行相关 pytest、全量 pytest、npm run build，并真实点击 Ripple 默认/最新及第1/2/3/末页，核对DOM卡片数量和顺序。
- 审查 diff 和工作区后提交，不推送或重启；运行态若需重新加载新后端，明确说明并取得对应动作授权。

## Risks / rollbacks

- 官方默认排序可能依账号/上下文变化：绑定账号与请求条件，保留证据时间，按同账号比较，不承诺跨账号一致。
- 官方列表未来超过安全上限或变化：返回截断状态与观察到的来源数，重新确认分页/游标机制，禁止静默丢尾部。
- 两次来源读取之间活动增减：各自快照保存独立成员与序号，UI固定一个批次翻页，更新后重新计算页数。
- 缓存/新接口出错：旧接口和数据保留，可回退页面实现；不通过删库修复排序。
- 活动规则字段仍可能不完整：本计划不把任务预览当作完整获奖规则，也不增加任何无证据结论。
