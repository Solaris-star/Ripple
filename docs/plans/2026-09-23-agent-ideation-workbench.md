## 1. Goal / Non-goals

目标：让用户从账号定位出发，在指定平台或账号运营的平台范围内，取得有来源依据、可比较、可制作的选题候选；选定方向后，由 Agent 与用户共同形成可编辑的内容策划单，再进入既有内容工作台。

推荐主路径：账号策略 → 读取热点/活动/已有内容 → 候选选题 → 用户定题 → 内容策划单 → 用户确认 → 主稿/平台版本 → 创作排期/发布审核。

选题库负责“做什么、为什么做、准备怎么做”。内容工作台负责正文、脚本、素材和平台版本。发布管理继续负责目标账号、审核与执行，选题操作不能越过发布审核。

非目标：首版不做无人值守发文、模型预测爆款概率、自动购买数据、全平台爬虫重构、多个独立聊天产品、复杂团队审批链、全仓数据库迁移或向量数据库建设。不为了凑数强行关联热点和活动。

## 2. Success criteria（可验证）

### 功能正确性

1. 用户选择小红书、抖音为目标平台时，结果只包含这两个平台的候选方案；微博可以是线索来源，不会被误认作目标发布平台。
2. 没有合适热点或活动时，可以生成赛道常青题，并说明没有关联活动的理由。纯活动模式不再要求同时选择热点来源。
3. 每条热点/活动引用可回到本次任务真实读取的源记录，带抓取时间、规则版本和账号可见范围。服务端拒绝伪造 source_ref 和越权账号引用。
4. 已过投稿截止的活动不作为可报名机会；资格未知与已满足分开；活动限制 AI 使用时，方案与后续生成能力遵守对应限制。
5. 选定候选后，角度、目标平台、证据引用、活动约束和待核实事项完整保留。重命名标题不改变选题 ID。
6. 同一核心选题的多个平台方案共享父选题，分别保留切入角度、形式和约束。同一平台不同账号的私有来源不能交叉引用。
7. 深化结果是可编辑、可追溯的策划单；用户可锁定已确认段落。Agent 的修改先作为建议，不覆盖用户已编辑内容。
8. 同一策划版本连续点击“进入制作”不会产生重复主稿。主稿可追溯 idea_id、brief_revision 和来源快照。
9. 切页、刷新或断线后，可恢复候选批次与已保存的策划单。部分平台失败时保留其他已校验结果，重试仅处理失败部分。
10. 老选题的 ID、标题、备注、原状态及日期迁移后不丢失。旧“已完成”不自动解释成“已发布”。

### 性能与费用目标

列表加载与 Agent 执行分离。普通进入页面不触发模型，也不强制刷新平台采集。已有候选列表首屏目标 1 秒内，已缓存回切目标 300 毫秒内；这是实施验收目标，须在 5173/7860 分别验证。

提交任务后先返回 run_id 和可观察状态，目标 1 秒内反馈。模型产出耗时取决于所选 Runtime、资料范围和授权研究预算，UI 不承诺固定秒数。候选通过结构校验后分批显示，不等所有平台结束。

每次生成明确 Runtime、输出数量和研究范围；费用有提供方实际 usage 才显示已知值，未知时显示“用量未返回”。页面刷新、断线重连、重复点击不得重复发起付费任务。

## 5. 功能架构与页面职责

### 选题库内部两个主要工作区

**推荐候选**：显示当前画像的候选，包含 Agent 推荐、从热点/活动带入的线索。默认卡片/列表视图，支持按目标平台、主题、来源类型、可制作程度筛选，历史批次单独入口。

**我的选题**：用户手动记录或从候选中选定的内容方向。按待深化、待确认、可制作、制作中查看；看板是此处的可切换视图。收藏待考虑的候选不自动成为进行中的任务。

归档和不感兴趣的候选可找回，不与已选题混在首屏。页面名继续使用“选题库”，不增加新的顶级导航。

### 跨页面衔接

| 入口 | 带入选题库的内容 | 行为 |
| --- | --- | --- |
| 热点雷达“围绕此热点找选题” | 真实趋势引用与快照时间 | 固定此线索，按当前画像和目标平台生成角度 |
| 活动广场“围绕此活动找选题” | 活动 ID、规则版本、参与平台、账号可见性 | 先校验资格/时效/AI 限制，再给符合规则的候选 |
| 选题库“帮我找选题” | 当前画像、平台、目的、制作约束 | 自动召回合适热点/活动，也允许常青题 |
| 选题库“我已有想法” | 手写标题、备注或明确授权的资料 | 跳过批量推荐，进入角度澄清和策划深化 |
| 已确认策划单“进入制作” | 选题 ID、策划版本、平台方案、来源与规则 | 幂等建立/打开主稿，在内容工作台继续生成正文与素材 |

## 6. 功能逻辑

### 6.1 输入策略

界面区分三类信息：

1. 账号策略：赛道、目标受众、差异化、内容支柱、风格、禁区、已有素材和制作能力。
2. 本次意图：目标平台、创作目标、数量、投入时间、偏好的形式与主题。
3. 来源范围：热点来源、活动来源、用户指定材料，以及是否允许新增外部研究。

“热点来自微博”不等于“发布到微博”。“已绑定抖音账号”也不等于该账号已满足所有活动资格。画像 ID 与真实发布账号 ID 分开保存。

平台模式：
- 指定平台：仅生成所选目标平台方案。
- 智能分配：在用户当前选中的运营平台集合内推荐主平台与备选平台。
- 多平台覆盖：每个候选有一个核心角度和多个平台方案；覆盖不足时说明原因，不给不适合的平台硬凑内容。

### 6.2 来源组合

支持赛道常青、热点切入、活动投稿、热点与活动自然结合四种来源路径。热点和活动均为可选输入；用户明确指定某活动时，其参与规则成为硬约束。

检索优先使用已同步缓存。热点按同事件聚类、保留多来源，不能简单相加跨平台热度。没有历史观测就不能生成“热度上涨百分比”。活动按目标平台、截止、账号可见性、内容形式和 AI 政策过滤。

活动关联需记录用途：participate（参与投稿）或 reference（分析/解读素材）。不同用途的限制不同，跨平台引用一个活动不代表跨平台作品能参赛。

### 6.3 召回与排序

先过滤硬冲突，再判断账号匹配、受众价值、时效、差异化、制作可行性和证据完整度，最后做题材与角度多样性控制。

首版不展示爆款概率，不以一个裸露的 0–100 分数作为主决策。卡片展示推荐等级、两条具体理由、证据状态与成本假设；既有七维评估可作为展开项或对短名单按需运行。

相同事件的换标题要合并或提示重复；同一核心角度的不同平台表达保留为平台方案。与历史选题相近时说明“延续系列”或“重复风险”，保留用户主动做续集的选择。

### 6.4 候选信息契约

每个候选至少包含：稳定 ID、核心选题/角度、面向受众、用户价值、为什么现在做、推荐主平台、平台形式、来源引用、活动约束、素材需求、制作成本估计与假设、待核实事项、来源更新时间。

模型输出的 source_ref 必须来自当前任务实际读取的资料清单，平台 ID 必须来自能力登记表。字段缺失可局部重试；数据不支持的事实必须归入假设/待核实，不能由文本流直接写入正式选题。

### 6.5 定题后的深化

用户点击“选定并深化”后，候选转入我的选题。Agent 只对被选中的方向深挖，先形成策划单：
- 目标受众与内容目的；
- 核心结论/待验证问题与差异化；
- 标题方向、开头/封面表达；
- 分段提纲或脚本节奏；
- 各目标平台的形式与表达差异；
- 来源、事实核验与活动要求清单；
- 素材/实测/采访等人工工作与预计投入；
- 待用户确认的问题。

只追问影响制作的缺口；已有画像信息不反复询问。没有实测记录时只能给“实测计划”，不能写成用户已经完成的经历。活动禁止相应 AI 使用时，停止该类型的自动创作，并解释限制。

策划单支持局部调整：更换受众、缩小问题、降低成本、重做开头、只修改某平台方案、追加证据。用户确认的段落可锁定；Agent 修改以差异建议出现。

确认策划后进入内容工作台。深度正文、镜头素材生成、平台版本编辑继续放在原工作台，选题库不复制第二个编辑器。

### 候选卡与对比

候选卡只放决策所需摘要，不复制活动卡的全部规则。点击卡片打开右侧详情，分为“选题方案 / 来源依据 / 平台表达”。批量对比限制为 2–3 条，使用相同维度横向比较，减少长文阅读。

同题跨平台默认一张主卡，平台选项切换展示对应标题、开头和形式。切换平台不重新调用 Agent；已有方案直接读取。

### 深化界面

选定后在选题库内部进入策划详情，左侧为结构化策划单，右侧为仅绑定当前选题的 Agent 协作。每次改动明确作用域，例如“只重写抖音开头”，主操作为“确认方案并进入制作”。

不在批量生成期间锁住整个页面。任务栏显示真实阶段：读取资料、筛选机会、生成候选、校验来源；支持取消、离开、继续其他操作。后台任务记录在应用中持久化，不依赖某个前端弹窗存活。新结果提示不得自动切换用户当前画像或页面。

### 空态与失败态

未生成时提供明确开始入口；有旧结果时继续显示旧结果并标注时间。缺画像时只补赛道/受众/目标平台等必要项。某来源失效时列出不可用源并让用户选择继续，不把读取失败显示成“0 个可做选题”。

Agent 不可用时可记录/编辑已有选题，明确展示配置入口。重复推荐不覆盖上一批；保留收藏、已选和拒绝原因。

```text

    ↓
Ideation API（鉴权、任务/版本/幂等）
    ↓
策划编排器
  ├─ 读取画像与本次意图
  ├─ 查询热点、活动、历史选题和授权素材
  ├─ 生成候选与平台方案
  ├─ 校验 schema / 来源 / 约束 / 重复
  └─ 定题后研究与生成策划版本
    ↓
选题域存储（批次、选题、策划版本、来源快照、反馈）
    ↓ 用户确认
ContentLibrary / 平台版本 / ContentPlan / 原发布审核
```

### 工具与权限

发现阶段可用结构化只读工具：profile.read、trends.search、campaigns.search/detail、ideas.search、contents.summary、assets.search（用户授权范围）。这些是拟议工具名，最终按现有能力登记接入。

Agent 只提交 candidate/brief proposal。确认、建主稿、排期等写入动作由用户操作调用服务端检查；不把通用 shell、浏览器登录、发文或付费采集权限授予选题任务。外部内容作为资料，不作为执行指令。

### 任务生命周期

IdeaRun 状态：queued → running → waiting_user / partial / succeeded / failed / cancelled。

任务固定 workspace、画像快照、目标平台、来源范围及预算。状态与有效候选先落库，再推送事件。刷新通过 run_id + event_seq 恢复，失败重试不重生成已确认结果；服务重启时对不确定的付费调用标 interrupted，不自动无限重跑。

候选默认一次 6 个，先本地过滤再调用模型。候选阶段只做轻量方案，不给所有候选生成长稿。深化仅作用于已选方向。预算耗尽保留部分结果、显示缺口，不自动切换付费供应商。

## 9. 数据与接口建议

建议为新选题域新增独立 SQLite 文件，初期使用 5 张核心表；不把任务事件和候选历史塞回共享大 JSON，也不迁移全站业务存储。

| 记录 | 主要字段与职责 |
| --- | --- |
| IdeaRun | 请求快照、workspace/画像/平台范围、运行状态、游标、预算、Provider/Runtime、错误摘要 |
| Idea | 稳定 ID、核心角度、阶段、批次、画像、平台方案 JSON、约束、来源引用、主稿关联、版本 |
| BriefRevision | idea_id、revision、策划结构、锁定字段、用户/Agent 修改来源、确认状态 |
| SourceSnapshot | 源类型、源 ID、实际 URL、抓取时间、来源版本、访问范围、必要原文摘录/摘要 |
| Feedback | 选题/平台范围、选择/暂存/拒绝、可选原因、创建时间 |

第一版平台方案作为 Idea 内的结构化子对象，避免过早引入多层表关系。将来确有独立查询量再拆表。资料快照保存必要上下文，不保存账号 Cookie、API Key 或不必要的个人信息。

拟议 API：
- POST /api/idea-runs：提交任务，含 idempotency_key，返回 run_id。
- GET /api/idea-runs/{id} 和 /events：运行快照、已校验候选及断线恢复。
- POST /api/idea-runs/{id}/cancel：停止后续生成。
- GET /api/ideas：按画像、目标平台、阶段、来源、关键词分页。
- POST /api/ideas/{id}/select：定题，不自动创建正文。
- POST /api/ideas/{id}/develop：局部/完整深化，产生新策划建议版本。
- PATCH /api/ideas/{id}/brief：用户编辑，校验 expected_revision。
- POST /api/ideas/{id}/start-content：确认策划并建立/返回主稿，校验 expected_revision 与活动快照。

与既有 ContentLibrary 不同存储时，不能承诺跨库原子事务。使用稳定交接幂等键 idea:{id}:brief:{revision}:content，先创建或找回主稿，再补关联；失败重试恢复同一份主稿，不生成副本。

### 迁移

备份 _ideas.json，保留旧 ID/备注/日期/状态。旧 pending 进入“我的选题/待深化”，doing 进入“制作中/待关联内容”，done 保留“旧已完成”语义。缺画像或目标平台的记录标“旧记录待补上下文”，不猜测归属或污染其他账号推荐。

切换后 /api/ideas 兼容接口只委托一个数据源；不长期双写 JSON 和 SQLite。回滚需要导出迁移后新增/修改内容并对账，禁止覆盖用户迁移后的编辑。

## 10. Options considered → 推荐

A. 保留三列看板，仅增强推荐 Prompt：改动小，但候选比较、批次恢复、平台信息与深化阶段仍缺失。

B. 纯聊天式选题：自然语言自由，但难比较多个候选，长对话中的来源/平台状态不易核对。

C. 结构化候选 + 局部 Agent 协作：推荐。卡片用于决策、策划单承接深化、现有内容工作台承接制作。增加一个选题域存储和明确的异步任务接口，避免重做编辑/发布体系。

## 11. Phases / Steps

### Phase 1：完整最小闭环（首个可用版本）

Step 1：定数据契约与迁移。建立 IdeaRun/Idea/Brief/Source/Feedback 模型、平台规范 ID、来源归属与版本校验；实现旧 _ideas.json 兼容读取和迁移备份。验证旧数据不丢、跨画像隔离、并发版本冲突和幂等。

Step 2：做候选生成。复用画像模板和热点/活动服务，支持指定平台、自然匹配活动与无热点的常青题；建立可恢复任务及来源校验。验证活动截止、AI 政策、资格未知、不匹配来源排除和部分失败。

Step 3：改推荐候选页面。压缩顶部设置、候选卡/平台切换、暂存/拒绝、历史批次；“我的选题”保留进度视图。验证首次进入不调用模型、切页返回不丢结果、失败不显示假空列表。

Step 4：实现定题深化及内容交接。结构化策划单、局部建议、锁定字段、确认版本、关联主稿与平台方案。验证从候选到内容工作台的全流程；同版本重复点击只创建一份主稿；活动规则变化时需重新确认受影响约束。

Step 5：接创作排期。保留现有两个日历入口的职责，不新增第三套日历数据；用现有 ContentPlanService 承接创作计划，选题日历通过关联展示。选择日期/时区，不再默认写入今天；排期不自动发布。验证计划/主稿关联和既有日历兼容。

### Phase 2：推荐质量与协作提升

增加 2–3 候选对比、系列选题、用户材料优先、多平台版本差异提示、拒绝原因聚合；对采纳率低的样本做专项回归。偏好调整先给用户确认，不自动覆盖画像文件。

### Phase 3：显式启用的持续推荐与复盘

用户开启后按指定频率和预算生成新候选；同一来源变化不足不重复生成。接入已支持平台的真实发布指标，区分缺失数据与零数据，按平台/形式分别评估；不把相关性当确定因果。

## 13. Risks / rollbacks

- 来源不全：明确缺失/过期/不可访问，允许取消或使用现有范围，不生成虚构依据。
- 个性化过拟合：保留少量探索候选和手动调整，单次拒绝不永久改画像。
- 费用放大：预先确认范围、数量、工具与重试预算，输出部分成功而非自动无限追加。
- 资格/截止误判：源版本绑定、AI 限制硬检查、进入制作前重核；日期与时区分别保存。
- 缓存串数据：key 包含 workspace/画像/账号/目标平台/来源版本；确认和发布前不依赖过期缓存。
- 迁移与跨存储关联：备份、兼容委托、交接幂等、变更对账；回滚不丢迁移后新增内容。
- 多页面复杂度：选题库只做候选与策划，写作编辑继续在内容工作台；避免新增顶级导航和第二套发布系统。

## 14. Open questions / 推荐默认

建议确认首版包含“6 个候选 + 单/多平台选择 + 来源可追溯 + 定题深化 + 主稿交接”，默认手动启动，允许无热点/无活动，不自动发布。

技术上推荐独立选题域 SQLite；进入实现前以迁移样本与现有 ContentPlan/ContentLibrary 兼容测试核对落点。多人审批链、每日主动推荐、长期增长预测都不放进首个版本。
