# Plan: 选题库的主动发现与机会收件箱

状态：PLAN，等待用户确认。2026-09-23。
代码基线：bf46461；本轮仅只读探索及计划文档，不开启自动推荐、不调用模型、不刷新平台、不改业务代码或采集频率。

## Goal / Non-goals

目标：用户没有本次主题或明确需求时，依据已确认的长期账号策略，Agent 在来源发生有效变化时主动识别值得做的内容机会，形成有依据的选题候选。用户回来先看到可判断的机会，不需要每次填写目标、制作投入和要求。

推荐用户路径：确认一次账号策略并启用主动发现 → 已同步热点/活动有效更新 → 筛选机会 → 生成与校验 → 机会收件箱 → 用户选定 → 既有策划单 → 确认后进入内容工作台。

非目标：自动发布、报名、购买数据；自动生成所有候选的全文；突破平台风控；为了凑日报强行组合热点与活动；随机时刻调用模型；默认提高平台采集频率；首版迁移云端或引入新消息队列；擅自修改用户画像。

“每日”表示每天保持检查与判断；“发现机会”允许在任意一次有效来源更新后发生。保证每天新建固定条数与保证质量有冲突，默认允许当天没有新机会。

## Success criteria（可验证）

1. 本次目标和补充要求为空也可一键探索。长期策略至少包含账号方向、目标受众和允许的目标平台；缺失时一次性澄清，不把测试画像或模型猜测直接用作后台授权。
2. 只有显式启用的策略能产生自动模型任务，界面展示使用的 Runtime、预算/调用次数限制、来源与账号范围、通知方式。关闭策略后不再调度新的工作。
3. 不打开选题页面也能在后端运行时完成发现。单纯刷新页面或轮询状态不能触发新模型任务。
4. 新热点能匹配已存在的有效活动，新活动/规则更新也能匹配仍有时效的旧热点。不要求两边同时新建。
5. 源快照仅更新时间变化、同一热点跨源重复报道、同一事件热度轻微波动，不自动重复调用模型；实质规则、事实或参与窗口变化才进入重新评估。
6. 同一信号并发/重复投递不重复消费模型预算、不重复建候选。无法确认模型是否已执行的任务标记 outcome_unknown/interrupted，不自动重试付费调用。
7. 截止时间、剩余制作时间、目标平台、资格与账号可见性、AI 使用和独家等规则正确校验。不把“已经采集到”当成“当前账号可参加”。
8. 缺证据、规则不明或疑似误配可进入“待核实”，不能作为“高优先机会”通知用户。来源缺失不伪装成当天没有机会。
9. 候选提供本次触发原因、为什么适合账号、热点和活动的真实关系、来源/抓取时间/规则版本、制作成本假设、建议决策时间及未解决的问题。推测时效明确标为估计，不与官方截止混淆。
10. 方案没有自然适配的活动时可退为热点或常青方向；用户选择“只看热点+活动组合”时允许零结果，并说明原因。
11. 自动发现只新增/更新未确认的建议；不覆盖用户选定的标题、锁定的策划字段或主稿。规则过期/取消时提示受影响内容，不静默改写。
12. 同一来源可在多个批次被引用而不引起主键冲突；跨画像、账号和访问范围不串资料、不串结果、不串通知。
13. 临时预算预占与实际用量记账可核查；未知费用不能显示为0。额度耗尽后停止新增调用；非模型的变化检查可继续。通知上限与模型预算分别计数。
14. 关闭页面、断线、后端重启后可读到已完成候选；睡眠/关机期间明确显示离线。恢复后只对仍有价值的来源重新核对，不重放整夜全部已过时热点。
15. 时间测试使用可注入时钟与模拟来源事件，覆盖通知安静时段、时区、跨日额度、并发租约、暂停、重启及去重；不以真实模型或平台刷新充当自动化测试。

## Options considered → 推荐

A. 每天固定时间重跑“帮我找选题”：容易实现，但会错过两次调用之间的机会、重复分析相同资料，不能满足任意时刻的有效发现。

B. 固定短间隔全量调用模型：来源未变也花费Token，批次与重复候选快速膨胀，不推荐。

C. 来源有效变化驱动 + 每日轻量巡检 + 按质量投递：推荐。持续观察用规则/本地检索，只有有价值的变更进入Agent分析。调用时间由变化与预算共同决定，无固定推荐时刻要求。

## 产品与交互

### 两种使用方式共存

### 无头绪冷启动

先读取现有画像，显示“我将围绕这些方向替你找题”。画像缺失时只确认方向、受众、目标平台3项。默认投入和形式从画像/用户确认中带入，可覆盖。

一键探索先给少量不同方向：一个贴近账号日常内容、一个与当下机会相关、一个有限探索方向（来源不足时不伪造热点）。每条都能直接选定，避免再要求用户选择十几个参数。

### 反馈

“暂时没空”用于降低当前制作投入或延后机会，不判断为讨厌该赛道；“主题不相关”“活动不想参加”“做过相似内容”分别影响召回、活动偏好和去重。更改长期画像需要用户确认。

同一候选的新证据更新在原卡片上；被明确拒绝的同角度不换标题重推。出现实质新机会时可重新进入候选，但必须说明与被拒绝版本的差异。已选题只发规则/事实变化提示，保护人工策划与主稿。

## 发现与质量逻辑

### 触发与有效变化

- 热点首次出现、已观察到的持续上升/关键事实更新/多源确认：与当前仍有效的活动匹配。
- 活动新增、规则/资格/奖励/内容要求或截止变化：与当前仍有效的热点匹配。
- 活动临近真正投稿截止且制作时间仍足够：重新核对已关联候选，不简单新增一条同题。
- 账号策略被用户修改：对仍有效的来源做一次有界重评。
- 每日巡检或服务恢复：核对水位、来源可用性和机会时效，不全量重跑所有历史。

只有取样时间更新、标题空格变化、热度小幅抖动、请求失败等不构成新机会。热点增长需要历史观测证据；单次榜单不能推断爆发速度，也不能直接相加不同平台的热度数值。

### 组合先相关，后排序

本地归一/聚类 → 画像与授权范围过滤 → 热点和活动主题/形式/规则匹配 → 时间可行性 → 去重与多样性 → Agent给角度和可验证理由 → 服务端校验 → 投递。

顺序要求：先从缓存中按相关性取候选源，再限制送模型的数量。新热点×既有活动、新活动×既有热点均可；不机械计算所有笛卡尔积并送给模型。轻量筛选保留有限探索通道，避免纯关键词遗漏跨主题创意；探索同样受预算和证据约束。

可行性包括：制作时间 + 审核/投稿缓冲 + 平台时区必须容纳在官方参与窗口内。只有展示期的记录不假定拥有投稿截止。活动来源是否明确、身份是否有资格、是否允许AI/跨平台/非首发分别判断。

进入高优先收件箱的候选必须具体解释：为什么适合账号、为什么现在做、热点与活动如何自然关联、需要补什么材料、能否赶上窗口。模型的自评分只能参考，不能单独决定通知。

### 有效性和投递

机会状态：观察中 → 待核实 / 已推荐 → 已查看 / 已暂存 / 已选定 / 已拒绝 / 已失效。

不足以决策的线索可在“观察中/待核实”查看，不与可制作的主推荐混计。活动结束或事实被撤回则标失效；保持审计记录，不删除用户已采用的资产。

普通结果只增加站内新机会数。高相关、证据充分且窗口有限的机会才可使用用户授权的打断式提醒。通知发出前再次检查预算、候选有效性和策略状态；安静时段延迟通知，恢复时过期内容不补发。没有结果与服务失效是两个状态。

## 功能架构与数据

复用现有IdeationService、候选、策划版本和内容交接。新增一个主动发现服务，负责策略、变化合并、触发、预算和投递。首版仍在当前后端进程/Runner运行，采用现有SQLite的持久队列；不新增Redis/Celery或独立Agent群。

采集成功落盘 → 记录变更水位/事件 → 主动发现调度器 → 本地筛选 → 原子预占预算与租约 → 现有推荐执行器 → 严格校验与去重 → Idea候选 → 站内通知记录。

建议增加3类小表：
1. discovery_policies：enabled、persona及revision、允许账号/平台/来源、内容方向、默认制作约束、预算/通知/时区配置。
2. discovery_jobs：触发键、源版本集合、策略版本、水位、运行租约、dispatch状态、预算预占与已知usage、决策原因、IdeaRun关联。预算在事务内按活动预占/已消费求和，执行前写入，不能完成后才检查。
3. discovery_notices：idea及版本、投递渠道、状态、去重键、scheduled_at、sent_at。默认仅站内；后续外部提醒可以复用发件箱语义。

必要字段扩展：Idea.origin（manual/automatic）、opportunity_key、discovered_at、validity、trigger_summary；IdeaRun.policy_id/revision/trigger、执行来源；source_snapshots使用(run_id,id)联合键或等价作用域引用，另保留逻辑source_id、version、access_scope。先迁移回归，避免多批次来源冲突。

机会去重键依据画像/授权账号、主题事件、活动ID/参与用途、核心角度、目标平台。来源快照版本用于重评和更新，不把每次抓取时间都纳入新建候选键；平台版本归于同一核心候选。

现有异步运行器可以复用内容生成，但当前的进程内任务不能代替持久发现队列。采集文件与SQLite不在同一事务，落盘后事件可能丢失，所以恢复/周期巡检需按最后成功水位对账；采用可重复安全的事件处理，不承诺未经实现的跨存储exactly-once。

暂停策略会禁止新的dispatch，尚未调用模型的任务安全取消；已发送给Provider的请求可能已产生用量，不能声称取消即零成本。发布候选前再次检查policy revision和enabled；停用期间迟到结果可留历史，不推入主动收件箱。预算未知结果仍保留预占，待核对后释放，禁止无限自动重试。

## 实施 Phases / Steps

### Phase 1：可靠触发与上下文隔离

Step 1：修复来源跨批次引用、增加cache-only读取契约、限定画像/账号/平台的运行查询。为何：避免反复调用产生主键错误、偷偷发起采集和串画像结果。涉及 ripple/ideation.py、ripple/trends.py、web/app.py。验证同源两批次、空缓存/失效源、不调用Provider、跨画像隔离。

Step 2：新增发现策略和任务账本/预算/租约，开关默认关闭。接热点落盘与活动合并的轻量变更钩子，触发后只排队。为何：无页面时执行、重启恢复、限额与并发去重。涉及新 ripple/idea_discovery.py、ideation.py、后端生命周期/来源入口。验证重复事件、暂停、重启、未知结果、窗口水位、单次预占。

### Phase 2：机会质量和自动候选

Step 3：实现相关性召回、组合过滤、时间可行性、稳定机会键和拒绝抑制，复用已有推荐执行器但允许零候选。为何：定时生成6条不能替代高质量机会发现。涉及 discovery/ideation_engine、来源适配及测试。验证新旧信号交叉组合、无关高热/高奖励过滤、资格未知、AI政策、同题更新、严格组合零结果。

Step 4：每日轻量巡检和候选失效管理。为何：不能只靠新数据事件处理截止与来源失效。原采集频率和收费窗口不变。验证长时间无更新、临期但赶不及、服务恢复不重放、源离线与无机会区别。

## Risks / rollbacks

- 候选质量依赖源覆盖/时效：明确更新时刻和缺源，不能宣称全网实时捕获；上限是现有来源更新节奏。
- 本地机器睡眠/关机或后端停止不能工作。关闭网页可以后台运行的前提是服务仍存活；全天候运行需要之后明确选择常驻机器/部署环境，不能靠前端timer解决。
- 连续自动分析可能超支或重复：预算预占、事件合并、幂等dispatch、失败退避和未知结果隔离优先于高频率。
- Agent文本存在幻觉/注入风险：固定只读工具范围、服务端引用与规则检查、外部资料不执行指令、事实不充分不给高优先提示。
- 画像冷启动/偏好漂移：一次确认长期策略；拒绝原因区分当前没空与长期不喜欢，策略更新由用户确认。
- 回滚先关闭发现策略、排空未dispatch队列；保留已完成候选/通知账本与预算审计。SQLite模式迁移先备份，回滚不覆盖用户新增选题。
